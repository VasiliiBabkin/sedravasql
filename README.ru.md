# SedravaSQL — 0.1.0-alpha.1

**Экспериментальная встраиваемая база данных на Rust и SQLite.**

[English](README.md) · [Подробный контракт](docs/IMPLEMENTED_V0_1.ru.md)

> Исполняемый прототип реализован, проверен на Ubuntu Linux x86_64.
> **Не используйте для важных или производственных данных.**
> Это ограниченный интерфейс ключ/значение, **не** полноценный
> SQL-сервер или замена PostgreSQL.

## Сборка и проверка

Требуются Rust 1.85+, Cargo и C-компилятор
(для сборки SQLite в составе проекта).

```sh
git clone https://github.com/VasiliiBabkin/sedravasql.git
cd sedravasql
cargo build --locked
cargo test --locked --all-targets
python3 scripts/verify_local.py
```

Сам бинарник не требует Python. Независимый Python-скрипт проверяет
его как отдельный процесс в изолированных временных каталогах.
Аварийные тесты работают только в debug, не в release.

## Минимальный пример

```sh
mkdir -m 700 -p /tmp/sedravasql-demo
DB=/tmp/sedravasql-demo/data.sqlite
BIN=./target/debug/sedravasql
"$BIN" init "$DB"
"$BIN" plan-put "$DB" demo greeting "Привет"
"$BIN" put "$DB" demo greeting "Привет" \
  --expect 0 --request-key example-request-0001
"$BIN" get "$DB" demo greeting
"$BIN" audit "$DB" 10
"$BIN" verify "$DB"
"$BIN" backup "$DB" /tmp/sedravasql-demo/backup.sqlite
```

Второй идентичный вызов `put` с тем же ключом возвращает
`"replayed": true`, а устаревшая ревизия для нового запроса
отклоняется. Удаление требует `plan-delete`, потом `delete`
с `--confirm`, ревизией и новым ключом запроса.

| Возможность | Статус |
| --- | --- |
| SQLite, WAL, synchronous=FULL | Реализовано |
| Типизированный API ключ/значение, параметризованный CRUD | Реализовано |
| Preview + проверка ревизии (CAS) + подтверждение удаления | Реализовано |
| Идемпотентные квитанции + аудит в одной транзакции | Проверено на VDS |
| Конкурентные операции нескольких процессов | Проверено на VDS |
| Резервная копия через SQLite Backup API | Проверено на VDS |
| Неизвестные схемы и версии | Отклоняются, автоматической миграции нет |

| Произвольные SQL-запросы, свои таблицы, SQL-сервер | Не реализовано |
| Проверенное восстановление после потери питания | Не подтверждено |
| Шифрование, ACL, репликация и production | Не реализовано |

## Экспериментальный независимый движок

В отдельном [Rust crate native-engine](native-engine/) появился ограниченный
локальный append-only журнал без SQLite: атомарные многоключевые операции,
CAS, ключи идемпотентности и отдельный CLI для испытаний. Это **не**
стабильная СУБД, не полноценный SQL и не замена существующей SQLite-базы
Sedrava A5/A6. **Для важных данных не использовать.**
[Архитектура, ограничения и проверки](docs/SELF_HOSTED_STORAGE.ru.md).

Проверен [единый экспериментальный контракт пакетных транзакций](docs/BATCH_CONTRACT_A1.ru.md) для собственного журнала и отдельного SQLite-адаптера с общим набором тестов. Действующий API и интеграция Sedrava A6 не переключались.

**Эксперимент B1:** [проверка журнала и копирование подтверждённого префикса](docs/NATIVE_RECOVERY_COPY_B1.ru.md). Исходный файл не обрезается, lock не удаляется, работающий сервер A6 не переключается.

## Native B2: проверяемая резервная копия исправного журнала

Экспериментальные команды backup-plan / backup-copy создают
офлайн-копию **полного исправного native-журнала** в новый файл с
проверкой SHA-256. Никаких изменений SQLite API.
[Процедура и ограничения](docs/NATIVE_BACKUP_B2.ru.md).

## Native B3 — исследовательский snapshot

Отдельные команды snapshot-create и snapshot-verify создают
детерминированный материализованный снимок исправного остановленного
журнала в новый файл. Сохраняются записи, tombstone и история
квитанций. Восстановления базы из snapshot, checkpoint, ускоренного
старта или online-режима нет.
[Протокол B3](docs/NATIVE_SNAPSHOT_B3.ru.md).

## Native B4 — восстановление из snapshot

Экспериментальный restore-copy проверяет доверенный SEDRSNP1,
восстанавливает ВСЮ исходную историю транзакций в новый SEDRLOG1
и сверяет побайтовую SHA оригинала. Квитанции и ревизии сохраняются.
**Нет** переключения работающей базы, уменьшения журнала и
production-рекомендации.
[Процедура B4](docs/NATIVE_RESTORE_B4.ru.md).

**Официальный сайт:** https://sql.virtreal.ru/ — [русскоязычное руководство](https://sql.virtreal.ru/docs/). Исходники и способ воспроизводимой публикации в каталоге [site/](site/README.md). Сайт не предоставляет доступ к действующей СУБД.

## Native B5.1 — испытания повреждённых файлов

[Матрица повреждений и неполных файлов](docs/NATIVE_FAULT_MATRIX_B51.ru.md)
проверяет отказ при испорченных snapshot и защиту существующих
назначений. Это НЕ доказательство сохранности при отключении питания.

## Native B5.2 — контроль аварийного завершения

В экспериментальном движке NativeLog проверено 24 управляемых
завершения процесса записи и корректная операторская процедура
восстановления. Это не аппаратная power-loss сертификация.
Документ: docs/NATIVE_CRASH_B52.ru.md.

Экспериментальный B6: [атомарные транзакции 2–4 управляемых KV-ключей](docs/MANAGED_BATCH_B6.ru.md)
в исходных таблицах SQLite с общей квитанцией и явным opt-in.
Не production, не SQL-сервер и не собственный NativeLog.

Экспериментальный B7: [согласованное чтение нескольких ключей SQLite](docs/MANAGED_SNAPSHOT_B7.ru.md)
в одной транзакции без изменения схемы и без переноса на NativeLog.

NativeLog B8: [офлайн-индекс для чтения из проверенного снимка](docs/NATIVE_INDEX_B8.ru.md).
Снимок и журнал не меняются; все поиски сначала выполняют полную
верификацию индекса. Не используется как индекс работающей базы.

NativeLog B9: прямое чтение записей из офлайн-индекса после
однократной полной проверки при открытии. Файл журнала
не изменяется; подробнее docs/NATIVE_INDEX_B9.ru.md.

**Native B10 (эксперимент):** диапазонное чтение из проверенного офлайн-индекса, [описание и тесты](docs/NATIVE_INDEX_B10.ru.md).
