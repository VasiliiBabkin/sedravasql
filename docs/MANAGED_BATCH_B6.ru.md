# SedravaSQL B6 — атомарная транзакция нескольких управляемых ключей

Дата: 24 ноября 2026. Эксперимент, не production.

Реализован самостоятельный API поверх существующих SQLite-таблиц records,
audit и receipts. Он не заменяет существующий SqliteBatchStore, который
использует engine_batch_*, и не переключает движок на NativeLog.

API Database:
- enable_managed_batches(): явное включение дополнительной таблицы
  managed_batch_receipts, без изменения user_version=1. Обычный
  Database::init не включает эту возможность автоматически.
- commit_managed_batch(scope, request_key, ops, response_json): в одной
  транзакции BEGIN IMMEDIATE меняет 2–4 разных ключа с обязательными
  ожидаемыми ревизиями, записывает отдельный аудит и квитанцию для
  каждого ключа, а также одну общую неизменяемую квитанцию.
- lookup_managed_batch(scope, request_key): читает сохранённый результат
  без изменения БД.

Входной ManagedPut: namespace, key, value, expected_revision.
Формат, ограничения длины, запрет NUL и идентификаторы соответствуют
исходному SedravaSQL. CAS проверяется для всех ключей ДО записи.
При ошибке хотя бы одного ключа откатывается всё. Повтор того же
полного набора операций с тем же ответом и request_key распознаётся
без повторной записи. Другие данные с тем же ключом — конфликт.

Для каждой записи используется отдельный детерминированный производный
request_key в старых audit/receipts. Это сохраняет исходное ограничение
UNIQUE(namespace,request_key), а общая квитанция сохраняет JSON
приложения (без автоматической очистки).

Сам API не понимает структуру Sedrava-состояния: вызывающая сторона
должна сама добавить его как один из проверенных ManagedPut, соблюдая
подпись и ожидаемую ревизию. Возможность не предоставляет анонимный
HTTP-API и не открывает SQL-запросы.

Проверки: cargo test --locked --offline --all-targets; cargo clippy
--locked --offline --all-targets -- -D warnings.

Добавлены пять тестов: три ключа (два пользовательских плюс состояние),
подробная проверка аудита и квитанций, идемпотентность после открытия,
независимые писатели, откат при старом CAS, неверные/дублирующиеся
аргументы, необходимость opt-in и выявление подделанной квитанции.
Старые методы чтения и записи не изменяются.

Не подтверждены производственная готовность, стойкость при реальном
отключении питания, полномочия пользователей, миграции и retention
данных, устойчивость к злоумышленнику с тем же системным UID.
