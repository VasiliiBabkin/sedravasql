# SedravaSQL — путь к собственной СУБД (ADR 0001)

Статус: экспериментальный прототип, 23 ноября 2026.

## Цель

SedravaSQL должна стать **самостоятельной СУБД**: собственный движок
хранения, транзакции, контроль целостности, исполнение запросов,
планирование, типы, диагностика и инструменты администратора.

SQLite остаётся действующей проверяемой опорой для интеграции с Sedrava
A5/A6, но **не является целевым ядром**. Нет автоматического переноса
существующих баз. Пользовательские данные не затрагиваются.

## Первый реальный шаг — SQLite-free native-engine v0.0.1

Отдельный Rust crate native-engine/ использует serde, serde_json и sha2,
**не требует rusqlite/SQLite**. Он предоставляет нестабильный
TransactionalStore API и отдельный бинарник sedravasql-native-preview.

- Эксклюзивный один писатель, приватный каталог Unix 0700, файл 0600 и lock.
- Атомарные пакеты из 1–16 разных ключей. CAS всех ревизий, PUT/DELETE,
  надёжные tombstone-ревизии и валидация до записи.
- Append-only журнал: одна транзакция — один кадр с размером, JSON
  и SHA-256 цепочкой. sync_all вызывается до подтверждения записи.
- Сохранённые request-key и результат: точный повтор после перезапуска.
- Повреждённый или оборванный кадр отклоняется при открытии без
  автоматической обрезки и без маскировки ошибки.
- После аварии lock остаётся. Только оператор после подтверждения, что
  прежний процесс остановлен, может разбирать состояние и снимать lock.
- Попытка открыть файл SQLite как native format не конвертирует его.
- Existing SQLite Database API и native Sedrava Server A6 не переключены.

## Локальная проверка независимого движка

Команды выполняются в корне клонированного репозитория:

    cargo test --manifest-path native-engine/Cargo.toml --locked --all-targets
    cargo build --manifest-path native-engine/Cargo.toml --locked --bin sedravasql-native-preview
    python3 scripts/verify_native_log.py

Пример с приватной временной папкой (не используйте путь к важным данным):

    mkdir -m 700 -p ./scratch-native
    BIN=./native-engine/target/debug/sedravasql-native-preview
    "$BIN" init ./scratch-native/demo.slog
    printf '[{"namespace":"demo","key":"hello","expected_revision":0,"change":{"kind":"Put","value":"Привет"}}]' > ./scratch-native/ops.json
    "$BIN" batch ./scratch-native/demo.slog request-example-0001 ./scratch-native/ops.json
    "$BIN" read ./scratch-native/demo.slog demo hello
    "$BIN" verify ./scratch-native/demo.slog

## Доказано и НЕ доказано

Набор автоматических тестов проверяет транзакции над двумя ключами,
отклонение частичных изменений, stale CAS, неизменяемую идемпотентность,
повторные открытия, удаление и восстановление записи, 50 последовательных
коммитов, повреждение кадра/заголовка и заблокированный второй процесс.

Отдельный Python smoke-тест запускает CLI как дочерний процесс. Два
**отладочных** аварийных выхода: после записи длины кадра и после sync_all.
Первый приводит к явной ошибке при повторном открытии до ручного
восстановления, второй восстанавливает коммит и точный replay.

**NO-GO: не использовать для ценных данных и production.**

Не проверены физическое отключение питания, отказ диска, data-loss от
контроллера, автоматическое восстановление журнала, бэкапы native формата,
многопроцессная конкуренция за записи, quota/retention, сборка для Windows,
disk-full, fuzz/property и долгосрочная совместимость форматов.

Каждое открытие линейно перечитывает журнал, каждое изменение временно
копирует состояние в памяти. Полный файл пока не ограничен по размеру.
SHA-256 обнаруживает случайное повреждение, **не** защищает от владельца,
который может заменить всю цепочку. Отдельный native формат нестабилен.

## Следующие контрольные точки

1. Общий backend-контракт и одинаковые тесты для native и SQLite.
2. Явное восстановление после незавершённого кадра, snapshot/checkpoint,
   backup/restore, защита от resource-exhaustion.
3. Независимый дисковый индекс (сравнение B+tree, LSM и append-only).
4. Типизированные таблицы и ограничения, парсер и исполнитель запросов.
5. Миграции, планировщик, конкуренция, безопасность, benchmark,
   воспроизводимые cross-OS, failure-injection и durability испытания.
6. Интеграция с Sedrava только после явно пройденных контрольных точек.

Дальняя цель — возможность писать части движка на Sedrava после
реализации в языке необходимых примитивов и независимых проверок.
Это пока **цель, не реализованное свойство**.

Связанный проект: https://github.com/VasiliiBabkin/sedrava

## Следующий завершённый технический шаг: Batch Contract A1

Для NativeLog и SQLite добавлен [единый экспериментальный контракт](BATCH_CONTRACT_A1.ru.md) с одинаковыми тестами. SQLite использует отдельные таблицы и не меняет данные A5/A6. Это не готовая процедура переноса; восстановление native-журнала после аварии и эксплуатационные гарантии по-прежнему не реализованы.
