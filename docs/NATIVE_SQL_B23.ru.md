# B23 — последовательные SQL-транзакции

`sql-sequential FILE REQUEST_KEY STATEMENTS_JSON` takes 1..15 bound statements, at least one DML statement. Unlike B20, a bounded per-address overlay evaluates statements in input order; SELECT/UPDATE/DELETE require primary-key equality. Ordinary SELECT projections only (no JOIN/aggregate/scan); UPDATE/DELETE require a matching row. INSERT checks current overlay state; committed tombstones cannot be reinserted; deleting a row then reinserting within one transaction is allowed. A newly inserted then deleted row has no durable row effect. Repeated changes coalesce to one final mutation per address, one revision increment; affected counts distinct final mutations, not statement count. Foreign keys are deferred to the final native frame. Typed reads are returned in SELECT order and stored with the durable receipt. Historical replay returns exact observations even after subsequent writes/restart. Existing B20 API and write fingerprint remain unchanged. SQL receipt size and native limits apply; no interactive BEGIN/COMMIT sessions, arbitrary SELECT or concurrent writers. A precommit conflict/invalid input leaves the journal unchanged. Not production-ready; older readers cannot interpret B23 receipts, so downgrade after B23 writes is unsupported.
