# B33 — долговременные квитанции COW (первый ограниченный этап)

Исследование от B32 af407e53d8511ea23859f0738c9bd7567dc33da8. Не SQL backend и не релиз.

`CowTree::commit_receipted(key, ops)` возвращает `Receipt { generation, replayed }`. SHA-256 идентификатора и однозначного упорядоченного представления пакета (ключи, ожидаемые ревизии, присутствие значения, длины и байты) сохраняются вместе с поколением. Точное повторение возвращает исходное поколение без записи и без повторного CAS, даже после обычных транзакций и перезапуска. Изменённый пакет с тем же ключом отклоняется. Неуспешный CAS не резервирует идентификатор. Область идентификаторов — одна база; авторизация не реализована на этом уровне.

Квитанции входят в checksummed manifest SEDRHDR4, публикуемый атомарно с новым корнем по протоколу B32. Старые заголовки 1–3 читаются; без квитанций сохраняется v3. Старые readers v4 не поддерживают. Проверяются количество, порядок поколений, уникальность ключей и нулевой padding. Compact copy переносит квитанции вместе с данными; копия затем независима. Кеш и актуальный manifest проверяются перед replay. Не допускается молчаливое вытеснение.

**Ограничение:** 48 квитанций на всю базу (72 байта на запись); при заполнении новые receipted запросы отклоняются, старые повторы продолжают работать. Обычные commit доступны. Это сознательно ограниченный формат для проверки атомарности, не готовый механизм длительного промышленного использования. Далее необходим масштабируемый отдельный индекс квитанций, затем миграция и интеграция SQL. Полный обход дерева и повторная проверка перед новой receipted транзакцией увеличивают стоимость. Квитанция хранит поколение, а не произвольный исторический SQL-ответ. Не является криптографической аутентификацией против владельца файлов.

Пять целевых тестов PASS (включая служебный child): повтор после restart/compact, конфликт payload и порядка, CAS и граница 48, некорректный manifest с пересчитанной checksum, process exits после pages/stage/publish с проверкой атомарной публикации данных и квитанции и безопасного retry. Очистка stale lock/stage выполнялась вручную после подтверждения завершения child; физическое отключение питания не проверялось.
