# Контракт транзакционного хранилища A1 — SedravaSQL

Статус: экспериментальный Rust API, 23 ноября 2026.

## Задача

Собственная СУБД не должна зависеть от SQLite. Чтобы заменить базовый
движок без изменения семантики операций, оба варианта хранения теперь
реализуют один и тот же нестабильный TransactionalStore.

- SQLite-free: native-engine/src/lib.rs, NativeLog.
- SQLite adapter: src/sqlite_batch.rs, SqliteBatchStore.
- Типы и правила проверки: native-engine (NativeMutation, NativeChange,
  NativeEntry, NativeCommit, validate_batch, batch_fingerprint).

Структура проекта пока не гарантирует ABI, совместимость на диске и
промышленную пригодность. Никакие существующие базы A5/A6 не конвертируются
и к новому API не подключаются автоматически.

## Семантика

- Запрос: request_key (ASCII 12–128 символов) и 1–16 уникальных
  пар namespace/key. Имена: ASCII, буквы, цифры, точка, дефис, подчёркивание;
  длина 1–128 байт.
- Операция: Put(UTF-8 без NUL, до 65 536 байт) или Delete существующей
  ненулевой записи. Delete сохраняет tombstone и его ревизию.
- expected_revision проверяется по каждому ключу. При несовпадении
  **ни один ключ** пакета не меняется.
- Каждый успешный пакет увеличивает последовательность ровно на 1.
  Все затронутые ревизии увеличиваются на 1. Ограничение 32 квитанций
  A3/A5 к этим отдельным экспериментальным интерфейсам не относится.
- Повтор request_key с идентичными операциями (включая порядок)
  возвращает первоначальные квитанцию и последовательность с replayed=true.
  Отличающийся повтор — конфликт, без каких-либо изменений.
- Ошибки валидации, конфликт CAS, частичная или повреждённая транзакция
  не должны публиковать успешный результат.

В NativeLog кадр коммитится в append-only журнал с контролем SHA-256
и sync_all. В SqliteBatchStore используется BEGIN IMMEDIATE и COMMIT;
транзакция включает таблицы записей, квитанций, метаданные последовательности
и аудит каждой операции.

## Изоляция старого SQLite

SqliteBatchStore::init вызывается **явно**. Он создаёт новые таблицы:

- engine_batch_meta;
- engine_batch_entries;
- engine_batch_receipts;
- engine_batch_audit.

Старые records, audit и receipts не заменяются, user_version 1
не повышается. SqliteBatchStore::open отвергает ещё не
инициализированную базу, не внося никаких изменений.

Новый адаптер сверяет каждую квитанцию с её операциями аудита при
открытии, включая порядок ключей и количество записей. Это
дополнительная логическая проверка, а не криптографическая подпись.
Бэкап выполняется через существующий SQLite Online Backup API.

## Воспроизводимые испытания

На Ubuntu x86_64 с Rust/Cargo 1.100.0 и локальным кэшем:

~~~sh
cargo fmt --all -- --check
cargo clippy --locked --offline --all-targets -- -D warnings
cargo test --locked --offline --all-targets
cargo test --manifest-path native-engine/Cargo.toml --locked --offline --all-targets
~~~

tests/batch_conformance.rs прогоняет **один и тот же набор операций**
через оба бэкенда: создание двух ключей, атомарное изменение, Delete,
tombstone, CAS, защиту от ABA, конфликт idempotency-key, восстановление
после перезапуска и серию из 46 подтверждённых транзакций.

Дополнительно SQLite тестируется с 8 параллельными подключениями,
резервным копированием во время записи и повреждением audit/receipt.

## Ограничения / NO-GO

Пока **не** реализованы автоматическое восстановление оборванного native
журнала, backup native формата, disk-full проверки, квоты, индексы
на диске, многопроцессная синхронизация native, схемы/SQL-слой,
конвертация из SQLite, стабильный формат, cross-OS и физические
испытания отключения питания.

Экспериментальный NativeLog не может автоматически восстановить
оборванный кадр: открытие откажет, stale lock удалять на автомате нельзя.
Отдельный SqliteBatchStore проверяет данные, но не является публичной
сетевой СУБД. Ни один бэкенд пока нельзя считать production-ready.

Дальнейшее отслеживание: https://github.com/VasiliiBabkin/sedravasql/issues/9
