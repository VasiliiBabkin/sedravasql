# B28 — выбор стратегии диапазонного чтения

База B27: 075597a707cde19cb6ddc31360b2c98fd9c3c295. [B28-A, исследовательская ветка дискового B+Tree](https://github.com/VasiliiBabkin/sedravasql/tree/research/b28-tree-sql), [отчёт эксперимента](https://github.com/VasiliiBabkin/sedravasql/blob/d816ed31be8ee87226829000518529a15e18ef4b/docs/NATIVE_SQL_B28_TREE_EXPERIMENT.ru.md). B28-A функционально корректен в испытанном контуре, но медленнее для большинства диапазонов; не включён в main. B25 остаётся отдельным прототипом.

## B28-B: упорядоченный Replay

SELECT и aggregate распознают ровно одну пару допустимых ASCII ID bounds PK >= lower AND PK < upper. При отсутствии точного первичного ключа или подходящего вторичного индекса используется BTreeMap::range в памяти (с исключающей пагинацией, namespace и верхней границей). EXPLAIN: primary_key_range. Все полученные строки декодируются и проверяются; дополнительные AND predicates, сортировка, DISTINCT, LIMIT и агрегации используют прежние правила. Tombstones входят в бюджет, но не в результат. Пустые/обратные диапазоны пусты; дублирующиеся или невалидные ID bounds идут по прежнему scan path. Точный PK и secondary equality сохраняют приоритет. JOIN и DML не меняются.

Прежний MAX_SCAN=4096 для range ограничивает число посещённых ключей внутри диапазона, а не всей таблицы. Как при PK lookup, типизированные строки вне диапазона не декодируются и не проверяются конкретным запросом. Проверки журнала при открытии, протокол записи, fsync, квитанции и формат хранения неизменны. Никаких новых дисковых файлов, кешей или зависимостей.

## Измерения

Один release executable, одна база на каждый из размеров 32/128/512/2048, 240 измерений на ширину и вариант, пять warmups, чередование порядка внутри каждой пары. Обычный запрос id>=? AND id<? против эквивалентного id>=? AND id>=? AND id<? (повтор нижней границы принудительно сохраняет прежний полный scan). Поэтому есть дополнительная стоимость разбора/сравнения в контрольном запросе; это не идентичные тексты и не SQLite. Проверяется точный результат каждой операции, read-only bytes и NativeLog.verify. ## Следующий архитектурный шаг

B25 disk layout (фиксированные hash-probed slots, JSON node/data pages, WAL для отдельных операций) не готов для роли SQL backend. Нужен исследовательский page-addressed storage с компактными бинарными узлами, динамическим ростом, bounded page cache и атомарной многостраничной транзакцией. Сначала отдельный эксперимент и проверка crash/recovery, только затем миграция SQL.
