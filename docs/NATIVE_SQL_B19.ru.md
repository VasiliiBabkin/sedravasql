# B19 — вторичные индексные определения, DISTINCT, HAVING

CREATE INDEX name ON Table(column) persists an immutable schema-bound definition as a native journal mutation with the same durable SQL receipt. Index names unique within a table, one definition per non-primary column. Index data is a derived in-memory BTreeMap, not a separate durable on-disk index. On first lookup or reopen rebuild from <=4096 validated rows (including tombstones for budget). Up to four cached indexes per exclusive NativeLog handle; invalidate affected table/catalog caches only after successful durable commit, including typed table writes. No changes to SEDRLOG1 frame encoding, existing write fingerprints, transaction format or raw KV contract. Equality predicates choose primary-key lookup first, then first matching secondary index, otherwise bounded table scan. EXPLAIN reports index_name and index_cached; cold lookup scans, warm lookup fetches matching keys. No disk index pages, range index scans, uniqueness constraints, DROP INDEX, online compaction, optimizer statistics or benchmark speed claims. Dedicated trusted journal; reserved namespaces must not be written directly.

SELECT DISTINCT for ordinary single-table projections; ORDER BY must name projected column. Dedup before LIMIT. HAVING supports AND of scalar comparisons against projected aggregate alias or grouped column; int literals/bindings for numeric aggregates incl. AVG, SQL null rejects predicate. Not DISTINCT aggregate/JOIN, no arbitrary HAVING expressions or OR. Existing limits apply.

VDS: 53 native + 21 SQLite Rust tests, strict Clippy and all CLI regressions PASS. 30 rows / 15 independent SQLite comparisons before and after index and updates; in-process cache warm/invalidation and reopen tested. No production claim.
